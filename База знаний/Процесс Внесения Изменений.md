## Краткое описание

Данный документ описывает стандартизированный процесс внесения изменений в корпоративную базу знаний компании PASS24.online. Процесс обеспечивает контроль качества документов, отслеживание изменений и согласование обновлений через систему ревью. Документ содержит пошаговую инструкцию от создания задачи до слияния изменений в основную ветку репозитория.

## Основной контент

### Назначение процесса

Процесс внесения изменений обеспечивает:

- **Контроль качества** — все изменения проходят проверку перед слиянием
- **Отслеживаемость** — каждое изменение связано с задачей (Issue) и имеет описание
- **Согласованность** — изменения согласовываются через систему ревью
- **Версионность** — все изменения фиксируются в истории Git
- **Стандартизацию** — документы соответствуют единым стандартам оформления

### Участники процесса

- **Автор изменений** — сотрудник или контрибьютор, вносящий изменения
- **Reviewer** — Алексей Хромов, ответственный за проверку и согласование изменений
- **Ответственный за актуальность** — владелец раздела или документа, который может быть привлечен для консультации

## Пошаговая инструкция

### Шаг 1: Создать Issue

**Что делать:**

Создайте Issue через терминал Cursor с помощью GitHub CLI:

```bash
gh issue create --title "Заголовок Issue" --body "Описание Issue"
```

Или создайте Issue интерактивно (откроется редактор):

```bash
gh issue create
```

**Структура описания Issue:**
- **Заголовок:** Краткое описание проблемы или предлагаемого улучшения
- **Описание:** Детальное описание:
  - Что нужно изменить или добавить
  - Почему это необходимо
  - Какой раздел/документ затрагивается
  - Ожидаемый результат

**Где:** Терминал Cursor

**Результат:** Создана задача с уникальным номером (например, #123). Номер будет показан в выводе команды.

**Примеры команд:**

```bash
# Простой пример
gh issue create --title "docs: Добавить инструкцию по работе с новым модулем PASS24.AI" --body "Необходимо создать инструкцию для отдела технической поддержки по работе с модулем PASS24.AI. Раздел: Тех. поддержка/PASS24.AI/"

# С указанием меток
gh issue create --title "fix: Исправить ошибку в регламенте обработки документов ЭДО" --body "В документе обнаружена неточность в описании процесса согласования" --label "bug,documentation"

# Интерактивный режим (рекомендуется для длинных описаний)
gh issue create
```

**Примеры заголовков:**
- `docs: Добавить инструкцию по работе с новым модулем PASS24.AI`
- `fix: Исправить ошибку в регламенте обработки документов ЭДО`
- `update: Обновить информацию о продукте PASS24.online`

### Шаг 2: Подготовить рабочую среду

**Что делать:**

**Для сотрудников компании (прямой доступ к репозиторию):**
1. Убедитесь, что у вас актуальная версия основной ветки:
   ```bash
   git checkout main
   git pull origin main
   ```

**Для внешних контрибьюторов (через форк):**
1. Создайте форк репозитория через GitHub CLI:
   ```bash
   gh repo fork akhromovRT/репозиторий --clone
   cd репозиторий
   ```
   Или создайте форк вручную на GitHub, затем клонируйте:
   ```bash
   git clone https://github.com/ваш-username/репозиторий.git
   cd репозиторий
   ```
2. Добавьте основной репозиторий как upstream:
   ```bash
   git remote add upstream https://github.com/akhromovRT/репозиторий.git
   ```
3. Получите актуальные изменения:
   ```bash
   git fetch upstream
   git checkout -b main upstream/main
   ```

**Где:** Локальный компьютер, терминал

**Результат:** Готовая рабочая среда с актуальной версией базы знаний

---

### Шаг 3: Создать ветку для изменений

**Что делать:**
1. Убедитесь, что вы находитесь в ветке `main` и она актуальна
2. Создайте новую ветку с понятным названием:
   ```bash
   git checkout -b feature/краткое-описание-изменения
   ```
   или
   ```bash
   git checkout -b bugfix/issue-номер
   ```

**Где:** Локальный компьютер, терминал

**Результат:** Создана и активирована новая ветка для работы

**Рекомендации по именованию веток:**
- `feature/add-pass24-ai-instruction` — для новых документов
- `bugfix/issue-123` — для исправления ошибок
- `update/product-description-pass24-online` — для обновления существующих документов
- `docs/update-readme-op` — для обновления README файлов

**Важно:** Используйте понятные названия на английском языке с дефисами вместо пробелов

---

### Шаг 4: Внести изменения в документы

**Что делать:**
1. Откройте нужные файлы в редакторе
2. Внесите изменения согласно требованиям:
   - Для новых документов — используйте [Шаблон статьи базы знаний](../agent_docs/Шаблон%20статьи%20базы%20знаний.md)
   - Для обновления существующих — следуйте [Инструкции по работе с базой знаний](../agent_docs/Инструкция%20по%20работе%20с%20базой%20знаний.md)
   - Обязательно заполните метаданные документа (версия, даты, автор)
   - Добавьте запись в раздел "История изменений"
3. Если создаете новый документ в разделе — обновите соответствующий README.md файл
4. Проверьте форматирование Markdown

**Где:** Редактор кода или текстовый редактор

**Результат:** Изменения внесены в документы

**Важно:**
- Следуйте единым стандартам оформления документов
- Используйте разделители `---` для визуального разделения крупных блоков
- Проверьте корректность ссылок на другие документы
- При создании нового документа обязательно обновите README раздела

---

### Шаг 5: Проверить качество документов

**Что делать:**
1. Проверьте соответствие шаблону статьи:
   - Заполнены ли обязательные разделы (метаданные, целевая аудитория, краткое описание)
   - Для процедур — есть ли пошаговая инструкция и контрольный чек-лист
   - Обновлена ли история изменений
2. Проверьте форматирование:
   - Корректность Markdown синтаксиса
   - Единообразие стиля оформления
   - Корректность таблиц и списков
3. Проверьте содержание:
   - Ясность и понятность текста
   - Отсутствие опечаток и грамматических ошибок
   - Полнота информации
4. Проверьте структуру:
   - Корректность ссылок на другие документы
   - Обновлен ли README раздела (если создан новый документ)
   - Правильность размещения файла в структуре папок

**Где:** Локальный компьютер, редактор

**Результат:** Документы соответствуют стандартам базы знаний

**Чек-лист проверки:**
- [ ] Метаданные документа заполнены полностью
- [ ] Указана целевая аудитория
- [ ] Есть краткое описание
- [ ] Для процедур — есть пошаговая инструкция
- [ ] Обновлена история изменений
- [ ] Проверено форматирование Markdown
- [ ] Проверены ссылки на другие документы
- [ ] Обновлен README раздела (если создан новый документ)
- [ ] Отсутствуют опечатки

---

### Шаг 6: Сделать коммит изменений

**Что делать:**
1. Проверьте статус изменений:
   ```bash
   git status
   ```
2. Добавьте измененные файлы в staging area:
   ```bash
   git add .
   ```
   или для конкретных файлов:
   ```bash
   git add путь/к/файлу.md
   ```
3. Создайте коммит с описательным сообщением:
   ```bash
   git commit -m "тип: краткое описание изменений"
   ```

**Где:** Локальный компьютер, терминал

**Результат:** Изменения зафиксированы в локальном репозитории

**Формат сообщений коммитов (Conventional Commits):**

- `docs: Добавлена инструкция по работе с PASS24.AI` — для новых документов
- `fix: Исправлена ошибка в регламенте ЭДО` — для исправления ошибок
- `update: Обновлено описание продукта PASS24.online` — для обновления существующих документов
- `docs: Обновлен README отдела продаж` — для обновления README файлов

**Типы коммитов:**
- `docs:` — изменения в документации
- `fix:` — исправление ошибок
- `update:` — обновление существующего контента
- `feat:` — добавление нового функционала/раздела (редко для базы знаний)

**Важно:** Сообщение коммита должно быть понятным и отражать суть изменений. При необходимости укажите номер Issue: `docs: Добавлена инструкция по PASS24.AI (#123)`

---

### Шаг 7: Отправить изменения в репозиторий

**Что делать:**

**Для сотрудников компании:**
```bash
git push origin название-ветки
```

**Для внешних контрибьюторов (через форк):**
```bash
git push origin название-ветки
```

**Где:** Локальный компьютер, терминал

**Результат:** Изменения загружены в ваш форк или ветку основного репозитория на GitHub

**Важно:** При первом push может потребоваться установить upstream:
```bash
git push --set-upstream origin название-ветки
```

### Шаг 8: Создать Pull Request

**Что делать:**

Создайте Pull Request через терминал Cursor с помощью GitHub CLI:

**Вариант 1: Интерактивный режим (рекомендуется)**
```bash
gh pr create
```
Откроется интерактивный редактор, где вы сможете заполнить заголовок и описание Pull Request.

**Вариант 2: Через командную строку**
```bash
gh pr create --title "Заголовок PR" --body "Описание PR" --base main --head ваша-ветка
```

**Вариант 3: С указанием Reviewer и связи с Issue**
```bash
gh pr create \
  --title "docs: Добавлена инструкция по работе с PASS24.AI" \
  --body "## Описание изменений
Добавлена новая инструкция по работе с модулем PASS24.AI для отдела технической поддержки.

## Что изменено
- Создан новый документ \`Тех. поддержка/PASS24.AI/Инструкция по работе с PASS24.AI.md\`
- Обновлен README раздела \"Тех. поддержка/PASS24.AI/\"

## Связанные задачи
Closes #123

## Чек-лист
- [x] Документ соответствует шаблону статьи
- [x] Заполнены все обязательные разделы
- [x] Обновлен README раздела
- [x] Проверено форматирование Markdown
- [x] Проверены ссылки на другие документы" \
  --reviewer akhromovRT \
  --base main
```

**Структура описания Pull Request:**
- **Заголовок:** Краткое описание изменений (можно использовать то же, что в коммите)
- **Описание:** Детальное описание:
  - Что изменено или добавлено
  - Почему это необходимо
  - Какие документы затронуты
  - Связь с Issue (используйте `Closes #123` или `Related to #123`)
  - Чек-лист выполненных проверок

**Где:** Терминал Cursor

**Результат:** Создан Pull Request, готовый к ревью. Команда выведет URL созданного PR.

**Дополнительные опции:**
- `--draft` — создать PR как черновик
- `--assignee @username` — назначить исполнителя
- `--label "label1,label2"` — добавить метки

**Примеры команд:**

```bash
# Простой интерактивный PR
gh pr create

# PR с указанием Reviewer
gh pr create --title "fix: Исправлена ошибка в регламенте ЭДО" --reviewer akhromovRT

# PR с привязкой к Issue
gh pr create --title "docs: Обновлен README ОП" --body "Closes #123" --reviewer akhromovRT
```

**Проверка статуса PR:**
```bash
# Посмотреть список открытых PR
gh pr list

# Посмотреть детали конкретного PR
gh pr view <номер-PR>

# Открыть PR в браузере
gh pr view --web
```

### Шаг 9: Прохождение ревью

**Что делать:**
1. Проверьте статус Pull Request:
   ```bash
   gh pr view <номер-PR>
   ```
   Или откройте PR в браузере:
   ```bash
   gh pr view --web
   ```

2. Дождитесь проверки Pull Request Reviewer'ом (Алексей Хромов)

3. Если есть замечания:
   - Просмотрите комментарии через терминал:
     ```bash
     gh pr view <номер-PR> --comments
     ```
   - Или откройте PR в браузере для удобного просмотра:
     ```bash
     gh pr view --web
     ```
   - Внесите необходимые исправления в той же ветке
   - Создайте новый коммит с исправлениями:
     ```bash
     git add .
     git commit -m "fix: Исправлены замечания ревью"
     git push origin название-ветки
     ```
   - Коммит автоматически добавится в существующий Pull Request
   - Ответьте на комментарии Reviewer'а через терминал:
     ```bash
     gh pr comment <номер-PR> --body "Ваш ответ на комментарий"
     ```
   - Или через браузер (удобнее для длинных ответов):
     ```bash
     gh pr view --web
     ```

4. После одобрения Pull Request будет объединен (merged) в ветку `main` Reviewer'ом

**Где:** Терминал Cursor и браузер (по необходимости)

**Результат:** Изменения одобрены и объединены в основную ветку

**Полезные команды для работы с PR:**

```bash
# Посмотреть список всех PR
gh pr list

# Посмотреть детали конкретного PR
gh pr view <номер-PR>

# Открыть PR в браузере
gh pr view --web

# Добавить комментарий к PR
gh pr comment <номер-PR> --body "Текст комментария"

# Посмотреть комментарии к PR
gh pr view <номер-PR> --comments

# Проверить статус проверок (CI/CD)
gh pr checks <номер-PR>

# Обновить локальную ветку main после слияния PR
git checkout main
git pull origin main
```

**Важно:** 
- Будьте готовы к конструктивной критике и предложениям по улучшению
- Отвечайте на комментарии вежливо и профессионально
- Вносите исправления оперативно
- Используйте `gh pr view --web` для удобного просмотра и ответа на комментарии

## Контрольный чек-лист

Перед созданием Pull Request убедитесь, что выполнены все пункты:

- [ ] Создана Issue с описанием проблемы или улучшения
- [ ] Создана ветка с понятным названием
- [ ] Изменения внесены в документы
- [ ] Новые документы соответствуют шаблону статьи
- [ ] Заполнены все обязательные разделы (метаданные, целевая аудитория, краткое описание)
- [ ] Для процедур добавлена пошаговая инструкция
- [ ] Обновлена история изменений в документе
- [ ] Обновлен README раздела (если создан новый документ)
- [ ] Проверено форматирование Markdown
- [ ] Проверены ссылки на другие документы
- [ ] Отсутствуют опечатки и грамматические ошибки
- [ ] Создан коммит с описательным сообщением
- [ ] Изменения отправлены в репозиторий
- [ ] Создан Pull Request с детальным описанием
- [ ] Указан Reviewer (Алексей Хромов)

## Типичные ошибки и их решение

| Ошибка | Причина | Решение |
|--------|---------|---------|
| Pull Request отклонен из-за несоответствия шаблону | Документ не соответствует стандартам оформления | Изучите [Шаблон статьи базы знаний](../agent_docs/Шаблон%20статьи%20базы%20знаний.md) и внесите исправления |
| Забыл обновить README раздела | При создании нового документа не обновлен README | Добавьте описание нового документа в README раздела |
| Коммит с неясным сообщением | Сообщение коммита не отражает суть изменений | Используйте формат Conventional Commits: `тип: описание` |
| Конфлиты при слиянии | Ветка устарела относительно main | Выполните `git checkout main`, `git pull`, затем `git checkout ваша-ветка`, `git merge main` и разрешите конфликты |
| Не указан Reviewer | Pull Request создан без указания Reviewer'а | Используйте флаг `--reviewer akhromovRT` при создании PR или добавьте через `gh pr edit <номер-PR> --add-reviewer akhromovRT` |
| GitHub CLI не установлен | Команда `gh` не найдена | Установите GitHub CLI: `brew install gh` (macOS) или см. [официальную документацию](https://cli.github.com/manual/installation) |
| Не авторизован в GitHub CLI | Команда `gh` требует авторизации | Выполните `gh auth login` и следуйте инструкциям |

## Критерии успеха

**Успешное завершение процесса определяется следующими критериями:**

- Pull Request одобрен Reviewer'ом и объединен в ветку `main`
- Изменения соответствуют стандартам оформления базы знаний
- Документы актуальны и содержат полную информацию
- README файлы обновлены при необходимости
- История изменений в документах ведется корректно
- Все ссылки на другие документы работают корректно
