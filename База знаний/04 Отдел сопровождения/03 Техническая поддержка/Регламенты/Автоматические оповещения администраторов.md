## Краткое описание

Документ описывает концепцию и требования к системе автоматических оповещений, направляемых администраторам объектов о двух ключевых событиях: **задолженности по абонентскому платежу** и **внештатном отключении системы**. Содержит классификацию событий, логику триггеров, рекомендуемые каналы доставки, шаблоны сообщений и критерии успешной реализации.

---

## Контекст и проблематика

Сейчас администраторы объектов узнают о критических событиях (задолженность по АП, аварийное отключение СКУД) реактивно — либо от пользователей, которые уже столкнулись с проблемой, либо после обращения в техподдержку PASS24. Это приводит к:

- Задержке реакции на отключение системы (пользователи не могут пройти)
- Накоплению задолженности без своевременного предупреждения
- Росту нагрузки на техподдержку PASS24 по однотипным вопросам
- Ухудшению клиентского опыта и риску оттока

**Цель:** Перевести оповещение с реактивной модели на проактивную — автоматически информировать администраторов объектов до того, как проблема стала критической для конечных пользователей.

## Основной контент

### 1. Классификация событий для оповещения

#### 1.1 Задолженность по абонентскому платежу

| Уровень | Триггер | Срочность |
|---------|---------|-----------|
| **Предупреждение** | До даты оплаты осталось N дней (рекомендуется: 7 дней) | Средняя |
| **Напоминание** | День наступления даты оплаты | Средняя |
| **Просрочка** | Оплата не поступила через 1–3 дня после даты | Высокая |
| **Критическая просрочка** | Оплата не поступила более 7 дней, риск приостановки обслуживания | Критическая |

**Важно:** Логика оповещений должна учитывать существующий процесс повышения АП — новые суммы должны отражаться в оповещениях сразу после подписания ДС (см. [Процесс повышения АП](../../02%20Процессы%20сопровождения/Процесс%20повышения%20АП%20для%20действующих%20клиентов%20с%20уведомлением.md)).

#### 1.2 Внештатное отключение системы

| Уровень | Триггер | Срочность |
|---------|---------|-----------|
| **Кратковременный сбой** | Система недоступна более 5 минут (контроллер не отвечает на ping/heartbeat) | Высокая |
| **Расширенный сбой** | Система недоступна более 30 минут без подтверждённого технического обслуживания | Критическая |
| **Массовый сбой** | Несколько объектов/контроллеров одновременно недоступны | Критическая |
| **Восстановление** | Система возобновила работу после сбоя | Информационная |

### 2. Каналы доставки оповещений

Рекомендуется использовать **несколько каналов** с учётом срочности события:

| Канал | Применение | Примечание |
|-------|-----------|------------|
| **Push-уведомление в мобильном приложении** | Все типы событий | Основной канал — высокая доставляемость, мгновенно |
| **Email** | Задолженность (все уровни), восстановление после сбоя | Для документирования и ситуаций, когда push не доставлен |
| **SMS** | Критическая просрочка, критический сбой | Резервный канал при недоступности push |
| **Уведомление в веб-интерфейсе** | Все типы событий | Баннер/плашка при входе в личный кабинет |

**Приоритет каналов по срочности:**

```
Критическая → Push + SMS + Email + Веб
Высокая     → Push + Email + Веб
Средняя     → Email + Веб
Информационная → Веб (+ Email опционально)
```

### 3. Адресаты оповещений

Оповещение должно направляться следующим ролям (настраивается для каждого объекта):

- **Администратор объекта** — основной получатель всех оповещений
- **Старший администратор / Управляющий** — копия при статусах «Просрочка» и «Критическая просрочка», критических сбоях
- **Менеджер по сопровождению PASS24** — автоматическое уведомление в CRM при критических статусах (для проактивной работы со стороны PASS24)

### 5. Логика и технические требования

#### 5.1 Мониторинг доступности оборудования

Для автоматической фиксации внештатных отключений необходимо:

- **Heartbeat от контроллеров** — контроллер СКУД должен отправлять сигнал доступности с заданным интервалом (рекомендуется: каждые 1–2 минуты)
- **Сервис мониторинга на стороне PASS24** — фиксирует пропуск heartbeat и формирует событие «Устройство недоступно»
- **Порог срабатывания** — оповещение отправляется после [N] пропущенных heartbeat подряд (рекомендуется: 3–5, т.е. 3–10 минут), чтобы исключить ложные срабатывания при кратковременных обрывах сети

#### 5.2 Мониторинг платежей

- Источник данных о задолженности — 1С или биллинговая система PASS24
- Оповещения формируются по расписанию (например, ежедневно в 10:00) на основе актуального состояния счёта клиента
- При повторных оповещениях об одной и той же задолженности должна соблюдаться частота: не чаще 1 раза в день (антиспам)

#### 5.3 Настройки для администраторов

Администраторы объектов должны иметь возможность:

- Выбрать, какие типы оповещений они хотят получать
- Указать предпочтительные каналы (push / email / SMS)
- Добавить дополнительных получателей (другие сотрудники объекта)
- Указать «тихие часы» (например, не беспокоить с 23:00 до 07:00 — кроме критических оповещений)

### 6. Схема процесса (события и действия)

```
СОБЫТИЕ: Задолженность по АП
    │
    ├─ T-7 дней → Push + Email (Предупреждение)
    ├─ T-0 дней → Email (Напоминание)
    ├─ T+3 дня  → Push + Email (Просрочка) + уведомление менеджера PASS24 в CRM
    └─ T+7 дней → Push + SMS + Email (Критическая просрочка) + эскалация в ОС

СОБЫТИЕ: Внештатное отключение системы
    │
    ├─ 5 мин недоступности    → Push + Email (Кратковременный сбой) + задача в тех. поддержке PASS24
    ├─ 30 мин недоступности   → Push + SMS + Email (Расширенный сбой) + эскалация
    ├─ Массовый сбой          → Push + SMS + Email всем администраторам затронутых объектов
    └─ Восстановление         → Push + Веб (информирование об окончании сбоя)
```

### 7. Требования к интеграции

| Компонент | Описание |
|-----------|----------|
| **Источник данных о платежах** | 1С / биллинговая система → API или синхронизация с PASS24.online |
| **Источник данных об устройствах** | Heartbeat-сигналы контроллеров → сервис мониторинга PASS24 |
| **Push-уведомления** | Firebase Cloud Messaging (FCM) или аналог — уже используется в мобильном приложении |
| **Email-рассылки** | SMTP-сервис (существующая инфраструктура PASS24) |
| **SMS** | Подключение SMS-шлюза (например, SMSC, СМСЦентр) |
| **Веб-уведомления** | Баннер / плашка в личном кабинете PASS24.online |
| **CRM (Битрикс24)** | Webhook или интеграция для создания задачи/уведомления менеджеру при критических статусах |

## Пошаговая инструкция по внедрению

### Шаг 1: Аудит текущего состояния

**Что делать:**
1. Проверить, есть ли в текущем продукте уже реализованные оповещения администраторам
2. Определить, какие данные о статусе контроллеров уже собираются и хранятся
3. Определить, есть ли API интеграция с 1С / биллинговой системой

**Результат:** Понимание существующей инфраструктуры и точек интеграции

---

### Шаг 2: Приоритизация событий

**Что делать:**
1. Совместно с командой определить, какие события внедрить в первую очередь
2. Рекомендованный порядок:
   - **Приоритет 1:** Внештатное отключение системы (прямое влияние на работу объекта)
   - **Приоритет 2:** Задолженность по АП (финансовые риски и отток)

**Результат:** Согласованный план разработки по фазам

---

### Шаг 3: Разработка механизма мониторинга устройств

**Что делать:**
1. Убедиться, что контроллеры отправляют heartbeat с нужной частотой
2. Реализовать сервис, фиксирующий пропуски heartbeat и формирующий события
3. Настроить порог срабатывания (рекомендуется 3–5 пропущенных сигналов)

**Где:** Отдел разработки (бэкенд)

**Результат:** Система автоматически фиксирует недоступность устройств

---

### Шаг 4: Разработка механизма мониторинга платежей

**Что делать:**
1. Настроить синхронизацию данных о задолженности из 1С / биллинга с базой PASS24.online
2. Реализовать джоб (по расписанию), который проверяет статус оплаты и формирует события

**Где:** Отдел разработки (бэкенд / интеграции)

**Результат:** Система автоматически фиксирует состояние оплаты по каждому клиенту

---

### Шаг 5: Реализация каналов доставки

**Что делать:**
1. Подключить/использовать существующий push-сервис для мобильного приложения
2. Настроить email-шаблоны и триггерные рассылки
3. При необходимости подключить SMS-шлюз для критических оповещений
4. Реализовать баннер/плашку в веб-интерфейсе

**Где:** Отдел разработки (фронтенд + бэкенд)

**Результат:** Каналы доставки настроены и протестированы

---

### Шаг 6: Настройка уведомлений в CRM (Битрикс24)

**Что делать:**
1. Настроить автоматическое создание задачи/уведомления менеджеру по сопровождению при критических событиях
2. Убедиться, что менеджер видит сводку по проблемным клиентам в своём интерфейсе

**Где:** Битрикс24, интеграционный слой PASS24

**Результат:** Менеджеры PASS24 видят критические события в CRM без ручного мониторинга

---

### Шаг 7: Тестирование и пилот

**Что делать:**
1. Провести тестирование на тестовом окружении: симулировать задолженность и отключение устройства
2. Запустить пилот на 3–5 клиентах, получить обратную связь
3. Скорректировать пороги срабатывания и частоту оповещений при необходимости

**Результат:** Система проверена, ложные срабатывания минимизированы

---

### Шаг 8: Rollout и документирование

**Что делать:**
1. Включить оповещения для всей клиентской базы
2. Уведомить администраторов объектов о новой функциональности
3. Обновить документацию для техподдержки

**Результат:** Система автоматических оповещений работает в продакшне для всех клиентов

## Критерии успеха

- Администраторы объектов получают оповещение о задолженности **минимум за 7 дней** до возможной приостановки обслуживания
- Оповещение о внештатном отключении доставляется **не позже чем через 10 минут** после фиксации сбоя
- Количество обращений в техподдержку PASS24 по теме «задолженность» и «не работает система» снижается минимум на 30%
- Администраторы могут настроить предпочтительные каналы и отказаться от нежелательных оповещений
- Менеджеры по сопровождению видят критические события в CRM без ручного мониторинга

## Риски и ограничения

| Риск | Вероятность | Влияние | Митигация |
|------|-------------|---------|-----------|
| Ложные срабатывания (частые push при нестабильном интернете) | Средняя | Высокое | Настроить порог: 3–5 пропущенных heartbeat подряд; добавить логику «тихих часов» |
| Администраторы отключают оповещения из-за спама | Средняя | Высокое | Ограничить частоту; обеспечить чёткую ценность каждого сообщения |
| Данные о задолженности не синхронизируются актуально | Средняя | Среднее | Настроить частоту синхронизации с 1С не реже 1 раза в день |
| Не все администраторы используют мобильное приложение | Средняя | Среднее | Email и веб-интерфейс как обязательные резервные каналы |
| Рост SMS-расходов при масштабировании | Низкая | Низкое | SMS только для критических событий; анализ стоимости перед внедрением |
