## Краткое описание

Документ описывает подход отдела разработки к тестированию продуктовых гипотез: спикеризация MVP, оценка трудозатрат, критерии готовности к тесту и приёмке результатов. Связывает HADI-циклы маркетинга с технической реализацией.

---

## Основной контент

### Связь с HADI-циклами

Маркетинг формулирует гипотезы в формате HADI (Hypothesis — Action — Data — Insight). Разработка отвечает за:
- **Action** — техническую реализацию действия (фича, MVP, изменение потока)
- Подготовку к сбору **Data** (инструменты, события, логирование)
- Обеспечение стабильности среды для чистоты эксперимента

См. [HADI-циклы для сокращения цикла сделки](../../03%20Маркетинг/HADI-тесты/HADI-циклы%20для%20сокращения%20цикла%20сделки.md)

---

### Принцип спикеризации (thin slicing)

**Цель:** Сократить время и затраты на проверку гипотезы.

**Подход:**
1. Выделить минимальный объём кода/фичи, достаточный для проверки гипотезы
2. Допустимо упростить UI, временно исключить edge cases
3. Допустим «ручной» сценарий вместо полной автоматизации — если это ускоряет тест
4. Фиксировать ограничения MVP и планировать доработку после валидации

**Важно:** MVP не должен вводить пользователей в заблуждение. Ограничения должны быть прозрачны для продукта и маркетинга.

---

### Процесс работы с гипотезой

| Этап | Кто | Действия |
|------|-----|----------|
| **1. Поступление гипотезы** | Продукт / Маркетинг | Гипотеза в формате HADI, метрика, срок теста |
| **2. Техническая оценка** | Разработка | Оценка трудозатрат на MVP, риски, ограничения |
| **3. Спикеризация** | Разработка + Продукт | Согласование минимального объёма для теста |
| **4. Реализация** | Разработка | MVP в спринте, подготовка к сбору данных |
| **5. Запуск теста** | Маркетинг / Продукт | Включение эксперимента, сбор данных |
| **6. Анализ результата** | Маркетинг / Продукт | Insight, решение: масштабировать / итерировать / отменить |
| **7. Доработка или откат** | Разработка | Полная фича или откат MVP |

---

### Критерии готовности к тесту

MVP готов к включению в эксперимент, когда:
- Действие (Action) из гипотезы технически реализуемо
- Сценарий теста воспроизводим для целевой аудитории
- Метрики можно собирать (логи, аналитика, события)
- Нет критичных багов, блокирующих тест
- Ограничения MVP зафиксированы и согласованы

---

### Оценка трудозатрат

При оценке MVP для гипотезы учитывать:
- Объём кода (новый функционал vs доработка существующего)
- Интеграции (API, аналитика, логирование)
- Время на тестирование и деплой
- Риски (зависимости, неопределённость требований)

**Рекомендация:** Оценка в story points или часах с указанием допущений. При больших допущениях — разбить на фазы (исследование → оценка → реализация).

## Пошаговая инструкция

### Шаг 1: Получение гипотезы

1. Получить формулировку гипотезы (Если… то…), действие (Action), метрику и срок теста
2. Уточнить контекст: где будет тест (продукт, канал, сегмент)
3. Зафиксировать в задаче/тикете

---

### Шаг 2: Техническая оценка

1. Разобрать, что нужно реализовать для действия
2. Выделить минимальный объём (MVP)
3. Оценить трудозатраты и риски
4. Предложить альтернативы (если есть более простой способ проверки)

---

### Шаг 3: Согласование MVP

1. Согласовать с продуктом/маркетингом объём MVP
2. Зафиксировать ограничения и план доработки при успешном тесте
3. Включить в backlog спринта

---

### Шаг 4: Реализация и приёмка

1. Реализовать по [Definition of Done](../02%20Спринты%20и%20процессы/Definition%20of%20Done.md) (с учётом упрощений для MVP)
2. Обеспечить сбор метрик
3. Передать продукту/маркетингу для запуска теста
