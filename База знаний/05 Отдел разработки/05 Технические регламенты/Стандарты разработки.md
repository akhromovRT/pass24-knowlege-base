## Краткое описание

Документ определяет базовые стандарты разработки: code review, git flow, линтеры, CI/CD и инструменты. Обеспечивает качество и единообразие кода.

## Основной контент

### Code review

**Принципы:**
- Все изменения кода проходят ревью перед мержем в основную ветку
- Ревьюер проверяет: логику, тесты, соответствие стандартам, безопасность
- Комментарии — конструктивные, с предложениями по улучшению
- Ревью выполняется в течение 1 рабочего дня (при наличии ревьюера)

**Что проверять:**
- Соответствие задаче и критериям приёмки
- Отсутствие избыточного кода и дублирования
- Покрытие тестами (где применимо)
- Соблюдение стиля кода (линтер)

---

### Git flow

**Структура веток:**
- `main` / `master` — стабильная ветка для продакшена
- `develop` *(опционально)* — интеграционная ветка
- `feature/<task-id>-<short-description>` — фичи
- `fix/<task-id>-<short-description>` — баги
- `hotfix/<description>` — срочные фиксы в проде

**Правила:**
- Ветки создаются от `main` или `develop`
- Мерж только через Pull Request / Merge Request
- Прямые коммиты в `main` — только для hotfix с последующим ревью

---

### Оформление кода

- Следовать принятому в проекте style guide (если есть)
- Линтер должен проходить без ошибок
- Имена переменных, функций, классов — осмысленные
- Комментарии — для неочевидной логики, не для очевидного кода

---

### CI/CD

- Сборка и тесты запускаются автоматически при push / PR
- Успешная сборка — условие для мержа
- Деплой — по принятой в проекте схеме (ручной/автоматический)

*Конкретные настройки зависят от стека и инфраструктуры.*

### Документирование

- README в каждом репозитории: назначение, как запустить, как деплоить
- API — документировать (OpenAPI/Swagger или аналог)
- Архитектурные решения — фиксировать в ADR (Architecture Decision Records) при значимых изменениях

## Контрольный чек-лист перед PR

- [ ] Код соответствует задаче
- [ ] Тесты добавлены/обновлены
- [ ] Линтер зелёный
- [ ] README/документация обновлена (если нужно)
- [ ] PR содержит описание изменений
