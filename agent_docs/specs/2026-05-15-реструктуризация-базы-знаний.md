## 1. Контекст и проблема

Корпоративная база знаний PASS24 сейчас разнесена по двум репозиториям:

- **`pass24-knowlege-base`** — «справочный слой»: ~295 Markdown-документов о продуктах, методологиях, регламентах, FAQ. Организован по отделам.
- **`Bitrix24-migration` → `переезд Б24/@Инструкции Битрикс24/`** — «процессный слой»: 51 инструкция (42 готовы, 9 в работе) по работе сотрудников в новой CRM Bitrix24. Организован по ролям (МПП, РОП, Админ, Бухгалтер, Общие регламенты) и блокам жизненного цикла.

Цель — свести оба слоя в **один новый репозиторий** с идеальной, легко поддерживаемой структурой.

### Выявленные проблемы текущей структуры

| Проблема | Пример |
|---|---|
| Дубликаты документов | «Цели маркетинга Q1 2026», «Оценка менеджеров по продажам» — по 2 копии |
| Раздел в двух местах | «Стратегия 2026» — и в `01 О компании/06`, и в `03 Маркетинг/` |
| Непоследовательная нумерация | ОП=`02`, Маркетинг=`03`, ОС=`04`; «Тех. поддержка» вложена в ОС |
| Метаданные не машиночитаемы | Шаблон использует Markdown-таблицу вместо YAML-frontmatter |
| Связи через относительные ссылки без контроля | Ссылки ломаются при переносе файлов |
| Опечатки и мусор в путях | «парнерского ПО», «Инструкции  по WEB» (двойной пробел), пустая папка `информация-экспорт` |
| Корневой README — чужой шаблон | «2030AI Project Template» |
| Два слоя знаний в разных репозиториях | Справочный и процессный слой не объединены |

## 2. Цели и ограничения

### Цели

- Единая структура, объединяющая все разделы компании в одном репозитории.
- Устойчивость к реорганизациям (продукты, стратегия не «прибиты» к оргструктуре).
- Невозможность дублей по построению — у каждого документа ровно один «дом».
- Единый формат статей и машиночитаемые метаданные.
- Удобная навигация и перекрёстность публикаций.
- Лёгкая поддержка: автоматические проверки и skills-команды сопровождения.

### Ограничения

- **Git-репозиторий — единственный источник истины и витрина** базы знаний. Сотрудники читают её прямо из репозитория (GitHub).
- **Bitrix24 — операционная система** компании (CRM/портал), не хранилище базы знаний. Инструкции по работе в Bitrix24 — это контент базы знаний.
- Миграция должна **сохранять Git-историю** каждого документа.
- «Переезд Б24» (миграция из старого Bitrix во второй) — завершённый процесс, отдельного учёта не требует.

### Не-цели

- Не переносим базу знаний в Wiki-модуль Bitrix24.
- Не вводим `[[wikilinks]]` как основной формат (ломает GitHub-витрину).
- Не переписываем содержание документов — миграция структурная.

## 3. Решение: каркас базы знаний

Выбран **Подход B — «доменный гибрид»**: верхний уровень — устойчивые бизнес-домены, а не оргструктура. Отделы — лишь один из доменов.

### Верхнеуровневая структура (9 разделов)

```
00 Навигация и стандарты    — как устроена БЗ: инструкция, шаблоны, глоссарий, индекс-MOC, конвенции
01 О компании               — обзор, оргструктура, адаптация/онбординг, бухгалтерия, админ, IT
02 Продукты PASS24          — вся линейка .online / .control / .auto / .admin / .key
03 Отделы                   — знания и процессы каждого отдела (Продажи, Маркетинг,
                              Сопровождение клиентов, Техподдержка, Инженерия и монтаж, Разработка)
04 Процессы и регламенты    — сквозные процессы: операционный ритм, управление задачами, согласования
05 Стратегия и аналитика    — стратегия 2026, рынок, конкуренты, HADI-гипотезы
06 Справочники и реестры    — объекты, клиенты, карты
99 Архив                    — устаревшее
```

### Правило единственного дома

> Документ служит **одному** отделу/роли → лежит в папке этого отдела.
> Документ служит **нескольким** отделам → лежит в `04 Процессы и регламенты`.
> Третьего не дано — у каждого документа ровно один адрес.

## 5. Движок базы знаний

### 5.1. Метаданные — YAML-frontmatter

Каждый документ начинается с YAML-frontmatter (GitHub рендерит его как таблицу — для читателя выглядит так же, как нынешняя таблица метаданных).

```yaml
---
title: Обработка нового лида
type: процедура                # справочник | процедура | регламент | скрипт | FAQ | обучение | стратегия
status: актуально              # черновик | актуально | требует обновления | устарело
department: Продажи
audience: Менеджер по продажам
role: МПП                      # опц. — для ролевых инструкций
author: Алексей Хромов
owner: Алексей Хромов           # ответственный за актуальность
version: 1.0
created: 2026-03-16
updated: 2026-05-15
tags: [битрикс24, лиды, crm]
---
```

История изменений остаётся в теле документа таблицей.

### 5.2. Теги — управляемый словарь

Закрытый словарь тегов в `00/Конвенции именования и оформления.md`. Теги строчными буквами через дефис. Фасеты:

- **Продукт:** `pass24-online`, `pass24-control`, `pass24-auto`, `pass24-key`, `pass24-admin`
- **Система:** `битрикс24`, `1с`, `эдо`
- **Тема процесса:** `онбординг`, `воронка`, `sla`, `интеграция`, `дебиторка`, `допродажа`

Новый тег добавляется только в словарь.

### 5.3. Перекрёстные ссылки — гибрид GitHub ⇄ Obsidian

| Элемент | Решение |
|---|---|
| Формат ссылок | Относительные Markdown-ссылки `[текст](../путь.md)` — единственный формат, нативный и для GitHub, и для Obsidian |
| Obsidian-vault | Папка `.obsidian/` коммитится с преднастройками: `New link format = Relative path`, `Use [[Wikilinks]] = OFF` |
| `.obsidian/workspace.json` | В `.gitignore` (персональное состояние окон) |
| Что даёт Obsidian | Граф связей, бэклинки, поиск по тегам и frontmatter |
| Что даёт GitHub | Кликабельные ссылки, frontmatter-таблица, рендеринг без поломок |

Канонический механизм связей — раздел «Связанные материалы» в теле документа + MOC-индексы.

### 5.4. Именование

| Объект | Правило | Пример |
|---|---|---|
| Раздел верхнего уровня | Числовой префикс `00–99` с запасом | `03 Отделы/` |
| Подпапка | Без номера, описательное имя | `Методология продаж/` |
| Подпапка-последовательность | Номер только где важен порядок | `0. Знакомство с системой/` |
| Обычный документ | Sentence case, без префикса | `Работа с возражениями.md` |
| Ролевая инструкция | `Роль — Действие` | `МПП — Обработка нового лида.md` |
| Датированная запись | ISO-дата в начале | `2026-02-02 — Планёрка.md` |

Запрещено: двойные пробелы, опечатки в путях, неоднозначные даты (`02-02-26`).

## 6. Навигация и поддержка

### 6.1. Система навигации — три уровня

1. **Мастер-карта** `00/Карта базы знаний.md` — единая точка входа со всеми 9 разделами.
2. **README раздела = MOC** — навигатор: назначение, документы с описанием, рекомендуемый порядок чтения, связи.
3. **Ролевые пути** `01/Адаптация/Пути адаптации по ролям.md` — маршруты адаптации для новичков.

### 6.2. Процесс поддержки

- Изменения — только через Pull Request с ревью (`Процесс внесения изменений.md`).
- Правило README: изменил документ → обнови README раздела (проверяется в CI).
- Ответственный = поле `owner` в frontmatter.
- Квартальный ревью статусов: прогон по `status` и `updated`.

### 6.3. Автоматические проверки (CI на Pull Request)

| Проверка | Что ловит |
|---|---|
| Линк-чекер | Битые относительные ссылки |
| Валидатор frontmatter | Отсутствие обязательных полей, тег вне словаря |
| Проверка README | Документ изменён, README не обновлён |

### 6.4. Skills-команды сопровождения

| Команда | Действие | Статус |
|---|---|---|
| `/kb-new` | Создать документ из шаблона с заполненным frontmatter | Создать |
| `/kb-check` | Проверить ссылки, frontmatter, осиротевшие файлы | Создать |
| `/kb-readme` | Пересобрать README раздела из frontmatter | Создать |
| `/kb-audit` | Отчёт: устаревшие документы, без `owner`, не обновлялись >6 мес. | Создать |
| `import-meeting`, `NewImport` | Импорт контента в базу знаний | Существуют |

## 7. План миграции

Новый репозиторий **клонируется из текущего** `pass24-knowlege-base` (наследует историю 295 документов). Имя исправляется: `pass24-knowlege-base` → `pass24-knowledge-base`.

| Этап | Содержание |
|---|---|
| **0. Подготовка** | Новый репозиторий из клона старого. Ветка `migration`, branch protection. Наполнить `00 Навигация и стандарты` |
| **1. Каркас** | Дерево папок `00–99` с README-заглушками |
| **2. Перенос текущей базы** | `git mv` по доменам (PR за PR). Снятие 3 дубликатов в архив. Чистка имён |
| **3. Влить инструкции Битрикс24** | Перенос 51 инструкции из `Bitrix24-migration` через `git subtree` (с историей). Раскладка по адресам |
| **4. Конвертация метаданных** | Скрипт: таблица → YAML-frontmatter для всех ~350 документов. Простановка тегов |
| **5. Связи и навигация** | Починка относительных ссылок. Сборка MOC: мастер-карта, README, ролевые пути |
| **6. Движок и автоматизация** | `.obsidian/` + `.gitignore`. CI. Skills `/kb-*`. Новый `README.md`, обновление `AGENTS.md`/`CLAUDE.md` |
| **7. Финал** | Сквозной аудит, прогон CI, слияние `migration` → `main`. Архивация старого репозитория с README-редиректом |

Каждый этап — отдельный Pull Request с ревью. `git mv` сохраняет историю; слияние репозиториев — через `git subtree`/`filter-repo`.

### Изменение авторского процесса

После объединения двухшаговый процесс (черновик в `Bitrix24-migration` → публикация в базу знаний) **отпадает**. Новые инструкции, включая «будущие процессы», создаются сразу в новом репозитории командой `/kb-new`. `Bitrix24-migration` сохраняет только техническую часть переезда (скрипты, маппинги).

### Риски

| Риск | Мера |
|---|---|
| iCloud-синхронизация мешает массовым `git mv` | Миграция при «отстоявшемся» iCloud; операции пакетами |
| Относительные ссылки ломаются при переездах | Чинятся на Этапе 5; остаток ловит CI-линк-чекер |
| Папка `@Инструкции Битрикс24` активно редактируется | На Этап 3 — снимок на конкретном коммите |
| Кириллица и пробелы в путях | `git mv` обрабатывает корректно при квотировании |
